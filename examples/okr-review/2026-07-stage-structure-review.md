>

## 这个示例验证什么

这不是一篇供 Agent 模仿口吻的复盘范文，而是一条完整的方法样本。它验证：

```text
事实回放
→ Coach 洞察
→ 用户修正洞察
→ 围绕一条线索复盘
→ 用户形成认识与判断
→ Coach 建议
→ 用户决定
→ 收尾并进入下一条
```

它也保留一次重要失败：

> 用户已经形成认识后，Coach 没有及时收尾，继续追问 Stage 4 与项目边界，导致月复盘滑向项目设计。

这个失败直接形成了 v0.2 的收尾规则。

## 一、事实回放

### 周期覆盖

2026 年 7 月证据包包含：

- 90 条有效 Daily Doing，覆盖 28 天。
- 5 周、13 个有效的每周 3 Things。
- 31 条 To-do，其中 25 条在导出时已完成。
- OKR Doing Dashboard、Happy Writer、Agent Meta、Personal Network Infrastructure Engineering 四个项目 Dashboard。
- 已有周复盘、O / KR 判断轨迹、大事件与用户在本轮补充的材料。

### 与本线索相关的事实

- OKR Doing Dashboard 正在从页面开发走向核心对象、项目模板、人生之书、复盘与数据安全的系统建设。
- Happy Writer 从 Web / PWA App 升级为 Happy Writer System。
- Agent Meta 从零散 Skill 开发走向能力地图、阶段候选与 Context Continuity。
- 多个项目开始使用 Stage、Phase、Work Item、Milestone 和 Asset 表达发展结构。
- 用户反复出现补录、记录不完整、项目事项与 3 Things / Daily Doing 重合或缺失的问题。
- OKR Doing Dashboard 项目页已经展示四个项目 Stage；阶段 03 为“搭起可持续演进的系统架构”。

## 二、第一次 Coach 判断及其失败

### 不够准确的判断

Coach 最初将 7 月概括为：

> 战线太长、缺少完成门，因此做了很多，却没有形成强烈完成感。

### 用户修正

用户明确指出：

> 这些项目不是散乱。它们正在走向系统和工程建设，而且这种系统工程不是一开始规划好的，是长出来的。

涉及：

- OKR Doing Agent
- OKR Doing Dashboard
- OKR Doing System
- Happy Writer
- Agent Meta

### 失败原因

最初判断把“多项目并行”直接解释成“需要聚焦”，没有先辨认这些项目之间共同出现的系统化趋势。

这类判断虽然听起来合理，但没有穿过表面现象，不构成合格的 Coach 洞察。

## 三、修正后的 Coach 核心洞察

### 表面现象

- 项目数量多。
- 记录密度高。
- 数据需要补录。
- 项目、3 Things 与 Daily Doing 之间存在重合和缺失。

### 排除错误诊断

问题不能简单归结为：

- 用户不够聚焦。
- 项目太多。
- 记录习惯不好。
- 需要再做一套更完整的计划。

### 主要矛盾

> 系统从真实实践中自然生长出来的速度，已经超过了对它进行命名、结构表达和数据连接的速度。

### 核心判断

> 7 月真正发生的变化，不是几个散乱项目同时推进，而是多个产品和 Agent 都开始从局部功能走向系统工程。Stage 等结构帮助用户看见了这种成长；当前落后的部分，是把项目结构与 3 Things、Daily Doing 和证据连接起来。

### 不确定性

- “系统正在自然生长”是用户已经确认的体验。
- 整个系统最终采用什么网络结构，当前还没有足够证据定型。
- Stage 4 的详细完成门属于项目设计问题，不应在本条月复盘中继续展开。

## 四、复盘

### Coach 问题 01

> 回到一起推演项目阶段的那一天：在区分 Stage 和 Phase 之前，哪些东西混在了一起；做出区分之后，究竟是什么一下子变清楚了？

### 用户的回答

在区分 Stage 和 Phase 之前，所有动作都是想到什么做什么：

- 这个不对，要改。
- 那个不对，也要改。
- 一会儿觉得需要推进这件事，一会儿又跳到另一件事。

事项依然能够推进，但整个项目没有清晰架构。所有行动像平铺的碎片：

- 没有 Chunk。
- 没有关联。
- 每处理一件事，都需要重新调动大量背景。
- 消耗脑力和精力。
- 容易犯错。

用户一直在追问问题究竟出在哪里。

后来出现了一个关键问题：

> 除了 Todo / Doing / Done，是不是还需要对整个项目有全局、结构化的认识？

最初尝试用 Phase，但真实项目可能出现十几个、几十个甚至上百个 Phase。仅仅把 Phase 排列起来，得到的仍然是碎片的点。

真正需要的是：

> 能够形成线、连接点，并像房屋钢筋水泥一样承重的整体框架。

### Coach 镜像

Coach 将用户表达镜像为：

> 当时缺少的不是更多事项，而是项目的发展坐标。Todo / Doing / Done 只能说明一项工作处于什么状态；Stage / Phase 用来说明整个项目正在形成什么、走到哪里，以及具体事项为什么在这里。

结构关系：

```text
Project
└─ Stage：项目经历的一次整体发展与能力跨越
   └─ Phase：完成这次跨越时经历的若干工作段
      └─ Work Item：当前可以推进的具体事项
```

这次镜像与用户的“承重结构”比喻一致，没有替用户增加新的心理解释。

## 五、用户形成的认识与判断

### 用户的认识

> 项目需要 Stage 这样的承重结构，才能把碎片事项组织成有方向的整体。

### 用户的判断

> 目前系统结构已经开始形成，但项目、3 Things 与 Daily Doing 的证据连接还没有跟上。

### 更完整的阶段认识

以下内容由用户在对话中的原话与已确认意思整理，尚未写入正式 Dashboard：

> 这些系统不是一开始规划好的，而是在解决真实问题的过程中逐渐长出来的。这个月反复跳出来的关键词是“结构”。结构让我能够从碎片中看见全局，也降低了处理复杂项目时持续重新判断的脑力消耗。
>
> 在只有 Todo、Doing、Done 的时候，所有事项都在同一个平面上，想到什么就处理什么。区分 Stage、Phase 和具体事项以后，项目开始拥有承重结构，每一项工作也开始有了位置和关联。
>
> 目前系统仍处于框架生长阶段。记录有时需要补录，项目、3 Things 与 Daily Doing 之间也存在重合、互补和缺失。下一步需要解决的，不是增加更多记录入口，而是让这些证据在保留各自来源的同时真正连接起来。
>
> 整个系统更像一个不断延伸的网络，而不是一个单独的圆。可能的结构原则是：整体是网络，局部是闭环。

## 六、Coach 建议与用户决定

### Coach 可以建议

#### 现在的沉淀动作

- 为 OKR Doing Dashboard 补充一张“项目阶段设计”推进事项与资产。
- 把这次关于 Stage、Phase、发展坐标和完成门的新认识更新到项目阶段定义。

#### 下个周期的验证动作

- 选择一条真实项目推进，走完“项目事项 → 本周 3 Things → Daily Doing → 证据”。
- 标出重合、互补和缺失，形成最小连接契约。

Coach 只能提出建议，不能直接创建事项、资产或下月计划。

### 用户的决定

- OKR Doing Dashboard 补一张“项目阶段设计”卡片事项和资产，并更新项目阶段定义的新认识。
- 下月打通“项目事项 → 本周 3 Things → Daily Doing → 证据”，标出重合、互补和缺失，形成最小连接契约。

## 七、本条复盘完成卡

```markdown
## 本条复盘完成

### 用户的判断

目前系统结构已经开始形成，但项目、3 Things 与 Daily Doing 的证据连接还没有跟上。

### Coach 建议

#### 现在可以做

- 为 OKR Doing Dashboard 补充一张“项目阶段设计”推进事项与资产，并更新项目阶段定义的新认识。

#### 下个周期可以验证

- 打通“项目事项 → 本周 3 Things → Daily Doing → 证据”，标出重合、互补和缺失，形成最小连接契约。

### 用户的决定

- [x] OKR Doing Dashboard 补一张“项目阶段设计”卡片事项和资产，并更新项目阶段定义的新认识。
- [x] 下月验证项目事项、3 Things、Daily Doing 与证据的连接。

### 暂不展开

- Stage 4 的详细完成门。
- 整个系统网络的最终架构。
- 所有项目的数据迁移和自动接线。
```

## 八、为什么此处必须收尾

此时已经满足本条线索的完成条件：

1. 用户已经说出“结构对我意味着什么”。
2. 用户修正并确认了核心洞察。
3. 用户形成了清楚的判断。
4. 用户已经确认现在与下月的行动。
5. 后续问题开始进入 Stage 4、项目边界和数据实现方案。

如果 Coach 继续追问“阶段 04 的完成门是什么”，复盘就会滑向项目咨询。这些问题应进入“暂不展开”，让用户确认本条复盘并返回下一条线索。

## 九、这个样本形成的方法规则

- 事实目录不能替代 Coach 分析。
- Coach 洞察必须找到主要矛盾，不用“事情太多、需要聚焦”一类通用建议敷衍。
- Coach 可以直指问题，但不能替用户拥有第一人称认识。
- 用户修正洞察是复盘成功的一部分，不是 Agent 失败后的例外流程。
- 项目、目标、大事件与跨项目模式都可以成为复盘线索。
- 用户形成认识后必须收尾；实施问题进入待跟进。
- Coach 建议与用户决定必须分开。
- 每条线索最多保留一个即时沉淀动作和一个下周期验证动作。
- 完成卡是线索闭环，也是进入下一条复盘的门。
